# Requirements — AI Mock Interviewer

## Introduction

The AI Mock Interviewer is a voice-driven, adaptive interview application built
for a hackathon. A candidate uploads their resume, selects a target role, and
runs a spoken mock interview. Questions are generated by an LLM using the
candidate's resume and chosen role as context. The AI speaks each question aloud
(text-to-speech), the candidate answers by voice (speech-to-text), and each
transcribed answer feeds back into the LLM to drive adaptive follow-up
questions. When the interview ends, the LLM produces a scored feedback report
that is rendered on the UI.

A defining constraint is **graceful degradation with zero API keys**: every
external integration (LLM, TTS, STT) has a fallback so the product is fully
demoable offline — the LLM falls back to a deterministic mock generator on the
server, and TTS/STT fall back to the browser's built-in Web Speech APIs.

## Requirements

### Requirement 1 — Resume upload and parsing

**User Story:** As a candidate, I want to upload my resume and have it parsed
into structured fields, so that the interview questions are grounded in my
actual background.

#### Acceptance Criteria

1. WHEN a candidate uploads a `.pdf`, `.docx`, `.txt`, or `.md` file THE SYSTEM
   SHALL extract its text and return a structured resume.
2. WHEN a candidate pastes resume text or selects the sample resume THE SYSTEM
   SHALL parse it into structured fields without requiring a file upload.
3. THE SYSTEM SHALL extract name, summary, skills, experience, projects, and
   education from the resume text using heuristic parsing.
4. WHEN parsing completes THE SYSTEM SHALL render the extracted structured
   profile back to the candidate.
5. IF no file or text is provided THE SYSTEM SHALL return a `400` error, and IF
   parsing fails THE SYSTEM SHALL return a `500` error.
6. THE SYSTEM SHALL cap uploaded files at 10 MB and reject oversized requests.

### Requirement 2 — Role selection

**User Story:** As a candidate, I want to choose the role I am interviewing for,
so that the questions and scoring match that role.

#### Acceptance Criteria

1. THE SYSTEM SHALL offer exactly three roles: Software Engineer, Product
   Manager, and Data Scientist.
2. WHEN a candidate selects a role THE SYSTEM SHALL use that role's focus areas
   and competencies to shape question generation and scoring.
3. THE SYSTEM SHALL keep role-specific prompt guidance server-side and expose
   only display fields (id, label, competencies) to the client.

### Requirement 3 — LLM question generation with resume + role context

**User Story:** As a candidate, I want the opening question to reflect my resume
and chosen role, so that the interview feels relevant and personalized.

#### Acceptance Criteria

1. WHEN an interview starts THE SYSTEM SHALL generate a first question using both
   the parsed resume and the selected role as context.
2. THE SYSTEM SHALL create a session identified by a unique id and store the
   asked question as pending until it is answered.
3. IF the LLM is not configured THE SYSTEM SHALL generate a deterministic mock
   question that references the candidate's name and top skill or project.

### Requirement 4 — Text-to-speech for questions

**User Story:** As a candidate, I want to hear each question spoken aloud, so
that the experience mimics a real interview.

#### Acceptance Criteria

1. WHEN a question is presented THE SYSTEM SHALL speak it aloud.
2. IF a server TTS integration (e.g. ElevenLabs) is configured THE SYSTEM SHALL
   synthesize and play the audio.
3. IF server TTS is unavailable or unconfigured THE SYSTEM SHALL fall back to the
   browser's built-in speech synthesis.
4. THE SYSTEM SHALL allow the candidate to replay the spoken question.

### Requirement 5 — Voice answers with speech-to-text

**User Story:** As a candidate, I want to answer questions by speaking, so that I
can practice verbal responses.

#### Acceptance Criteria

1. WHEN a candidate records an answer THE SYSTEM SHALL transcribe the speech to
   text.
2. IF a server STT integration (e.g. Whisper) is configured THE SYSTEM SHALL use
   it to transcribe recorded audio.
3. IF server STT is unavailable THE SYSTEM SHALL fall back to the browser's live
   speech recognition.
4. THE SYSTEM SHALL allow the candidate to type or edit the answer as a manual
   fallback.
5. IF transcription fails THE SYSTEM SHALL prompt the candidate to type the
   answer instead, without ending the interview.

### Requirement 6 — Adaptive follow-up loop

**User Story:** As a candidate, I want follow-up questions that react to my
previous answers, so that the interview adapts like a real conversation.

#### Acceptance Criteria

1. WHEN a candidate submits an answer THE SYSTEM SHALL commit it to the session
   history and clear the pending question.
2. THE SYSTEM SHALL generate each follow-up question using the full transcript of
   prior questions and answers.
3. WHEN the number of answered questions reaches the maximum (6) THE SYSTEM SHALL
   end the interview instead of asking another question.
4. THE SYSTEM SHALL allow the candidate to finish early and proceed to the
   report.
5. IF the LLM is not configured THE SYSTEM SHALL generate deterministic mock
   follow-ups using role-specific templates.

### Requirement 7 — Feedback report generation and rendering

**User Story:** As a candidate, I want a scored feedback report at the end, so
that I understand my strengths and areas to improve.

#### Acceptance Criteria

1. WHEN the interview ends THE SYSTEM SHALL generate a report containing an
   overall score, a summary, strengths, areas for improvement, per-competency
   scores, and per-question feedback.
2. THE SYSTEM SHALL render the report on the UI with the overall score,
   competency bars, and per-question feedback.
3. IF the LLM returns a malformed report THE SYSTEM SHALL fall back to a
   heuristic mock report rather than failing.
4. IF no answers have been recorded THE SYSTEM SHALL return a `400` error for a
   report request.
5. THE SYSTEM SHALL defensively default missing report fields so a partial report
   still renders.

### Requirement 8 — Integration capability detection and graceful degradation

**User Story:** As a hackathon presenter, I want the app to run fully without any
API keys, so that I can demo it reliably offline.

#### Acceptance Criteria

1. THE SYSTEM SHALL expose a health/capability probe reporting which integrations
   (LLM, TTS, STT) are configured, the available roles, and the maximum question
   count.
2. WHEN the client loads THE SYSTEM SHALL use the capability probe to choose
   server vs. browser voice paths and to display integration status.
3. THE SYSTEM SHALL run the full interview loop end to end with zero API keys
   using mock LLM output and browser-based TTS/STT.
4. WHEN a server TTS or STT integration is unconfigured THE SYSTEM SHALL respond
   with `501` so the client falls back to browser voice.

### Requirement 9 — Error handling and resilience

**User Story:** As a candidate, I want the app to handle failures gracefully, so
that a single error does not break the interview.

#### Acceptance Criteria

1. THE SYSTEM SHALL wrap backend route handlers so failures return a structured
   `{ error, detail? }` payload with an appropriate status code
   (`400`/`404`/`500`/`501`).
2. WHEN a session id is unknown or expired THE SYSTEM SHALL return `404`.
3. WHEN an answer is submitted with no pending question THE SYSTEM SHALL return
   `400`.
4. THE SYSTEM SHALL surface backend error messages to the candidate via a visible
   error banner.
5. IF the backend is unreachable THE SYSTEM SHALL show a connectivity message and
   block the interview UI until it recovers.
6. THE SYSTEM SHALL treat voice (TTS/STT) failures as non-fatal and continue via
   fallback or typed input.

## Out of scope (hackathon constraints)

- Persistence: sessions are held in memory and do not survive a server restart.
- Authentication, authorization, and rate limiting.
- Multi-instance/session sharing across servers.
- Persisted or exportable report history.
