# Design — AI Mock Interviewer

## Overview

The AI Mock Interviewer is a voice-driven, adaptive interview application. A
candidate uploads a resume, picks a target role, and runs a spoken interview in
which each question is generated by an LLM using the resume and role as context.
Answers are spoken, transcribed to text, and fed back into the LLM to produce
adaptive follow-up questions. When the interview ends, the LLM produces a scored
feedback report that is rendered on the UI.

The system is split into two deployable units:

- **Frontend** — React + Vite single-page app. Owns the interview UI, the client
  voice loop (MediaRecorder + Web Speech API), and browser fallbacks for
  text-to-speech (TTS) and speech-to-text (STT).
- **Backend** — Node.js + Express REST API. Owns resume parsing, session state,
  LLM orchestration (question generation, adaptive follow-ups, report), and the
  server-side TTS/STT integrations.

A defining design constraint carried through from the implementation is
**graceful degradation with zero API keys**: every external integration (LLM,
TTS, STT) has a fallback so the whole product is demoable offline. The LLM falls
back to a deterministic mock generator on the server; TTS and STT fall back to
the browser's built-in Web Speech APIs on the client.

This document describes the design as it is actually built. Code references use
`server/src/*.js` for the backend and `client/src/*` for the frontend.

## Architecture

```
┌────────────────────────── Frontend (React + Vite, :5173) ──────────────────────────┐
│  App.jsx  ── phase state machine: resume → role → interview → report                │
│    ├─ ResumeStep      upload / paste / sample resume                                │
│    ├─ RoleStep        pick Software Engineer | Product Manager | Data Scientist     │
│    ├─ InterviewStep   voice loop: speak question → record → transcribe → submit     │
│    └─ ReportStep      render scored feedback report                                 │
│  api.js   ── thin fetch client for /api/*                                           │
│  voice.js ── speakBrowser, playAudioUrl, createRecorder, BrowserSpeechRecognizer    │
└───────────────────────────────────────┬─────────────────────────────────────────────┘
                                         │ HTTP (Vite dev proxy /api → :4000)
                                         ▼
┌────────────────────────── Backend (Node + Express, :4000) ─────────────────────────┐
│  index.js       routes + in-memory session Map + MAX_QUESTIONS cap                  │
│    ├─ resumeParser.js   extractText (pdf/docx/txt) → structureResume (heuristic)    │
│    ├─ roles.js          role catalog (focus + competencies) injected into prompts   │
│    ├─ llm.js            generateFirstQuestion / generateFollowUp / generateReport   │
│    │                    + deterministic mock fallbacks                              │
│    ├─ tts.js            ElevenLabs synthesize() ; ttsConfigured flag                │
│    └─ stt.js            Whisper transcribe() ; sttConfigured flag                   │
└───────────────────────────────────────┬─────────────────────────────────────────────┘
                                         │ (only when keys present)
                    ┌────────────────────┼────────────────────┐
                    ▼                    ▼                    ▼
             OpenAI-compatible      ElevenLabs           OpenAI Whisper
             chat completions       text-to-speech       audio/transcriptions
             (LLM)                  (TTS)                (STT)
```

### Key architectural decisions

- **Stateless client, server-held session.** The frontend holds only a
  `sessionId` and the current question. All interview state (resume, role, Q/A
  history, pending question) lives in a server-side in-memory `Map`. This keeps
  the adaptive loop authoritative on the server and the client thin.
- **In-memory session store.** Sessions are a `Map` keyed by a `randomUUID()`.
  There is no persistence layer — a pragmatic choice for a demo. Sessions do not
  survive a server restart and are not shared across server instances.
- **Capability probe drives the client.** `GET /api/health` reports which
  integrations are configured. The client uses this to pick server vs. browser
  voice paths and to display integration badges.
- **Same-origin API via dev proxy.** The client calls relative `/api/*` URLs;
  Vite proxies them to the Express server on `:4000` in development.

## Components and responsibilities

### Frontend

| Component | Responsibility |
|---|---|
| `App.jsx` | Top-level phase state machine (`resume → role → interview → report`). Holds `resume`, `selectedRole`, `session`, `report`. Fetches `/api/health` on mount and stores `integrations` + `roles`. Orchestrates `startInterview`, follow-up transitions, report loading, and restart. |
| `ResumeStep.jsx` | Upload (drag/drop or browse; `.pdf/.docx/.txt/.md`), or load the built-in sample via pasted text. Calls `uploadResume` / `parseResumeText`. Renders the extracted structured profile. |
| `RoleStep.jsx` | Renders the role list from `/api/health`, captures the selected `roleId`, and triggers `Start interview`. |
| `InterviewStep.jsx` | The adaptive voice loop. Speaks each question (server TTS or browser), records the answer (server STT via `MediaRecorder`, or live browser recognition), submits it, and routes the response to a follow-up or completion. Also allows typing an answer as a fallback. |
| `ReportStep.jsx` | Renders the report: overall score, summary, competency bars, strengths, improvements, and per-question feedback. |
| `api.js` | Thin `fetch` wrapper. Normalizes errors (throws `Error(data.error)` on non-2xx). Server TTS/STT helpers return `null` on `501`/failure so the caller can fall back. |
| `voice.js` | Browser voice primitives: `speakBrowser` (SpeechSynthesis), `playAudioUrl` (server MP3 playback), `createRecorder` (MediaRecorder → Blob), `BrowserSpeechRecognizer` (live SpeechRecognition), `hasBrowserSTT`. |

### Backend

| Module | Responsibility |
|---|---|
| `index.js` | Express app, CORS, JSON body limit (2 MB), `multer` in-memory uploads (10 MB cap). Defines all routes, owns the `sessions` `Map`, and the `MAX_QUESTIONS` cap (6). |
| `resumeParser.js` | `extractText` (PDF via `pdf-parse`, DOCX via `mammoth`, else UTF-8) and `structureResume` (heuristic section splitting, skill dictionary matching, name/summary guessing, entry grouping). |
| `roles.js` | Static role catalog. Each role carries `focus` (prompt guidance) and `competencies` (scored dimensions). `getRole`, `listRoles`. |
| `llm.js` | `generateFirstQuestion`, `generateFollowUp`, `generateReport` against an OpenAI-compatible chat API, each with a deterministic mock fallback. Exposes `llmConfigured`. |
| `tts.js` | `synthesize(text)` → MP3 buffer via ElevenLabs. Exposes `ttsConfigured`. |
| `stt.js` | `transcribe(buffer, filename, mimetype)` → transcript via OpenAI Whisper. Exposes `sttConfigured`. |

## Data models

All models are plain JSON objects passed over the wire and held in memory. There
is no schema enforcement layer; shapes below reflect what the code produces and
consumes. Pseudocode uses structured notation since the codebase is JavaScript
without static types.

### Resume (produced by `structureResume`)

```
Resume {
  name:       string        // guessed from header lines; may be ""
  summary:    string        // summary/objective section, or first header lines
  skills:     string[]      // matched against SKILL_DICTIONARY
  experience: string[]      // grouped entries, capped at 12
  education:  string[]      // grouped entries, capped at 8
  projects:   string[]      // grouped entries, capped at 8
  rawText:    string        // original text, capped at 12000 chars (for prompting)
}
```

Note: the object is created client-first via the parse endpoints, then passed
back to the server on `interview/start`, where it is stored in the session. The
client treats it as opaque display data.

### Role (from `roles.js`)

```
Role {
  id:           string      // "software-engineer" | "product-manager" | "data-scientist"
  label:        string      // human-readable, e.g. "Software Engineer"
  focus:        string      // prompt guidance describing role focus areas
  competencies: string[]    // scored dimensions, e.g. ["Technical depth", ...]
}
```

`listRoles()` returns only `{ id, label, competencies }` to the client (the
`focus` prompt text stays server-side).

### Session (server-side, in `sessions` Map)

```
Session {
  role:            Role          // full role object incl. focus + competencies
  resume:          Resume
  history:         QAPair[]       // completed question/answer pairs
  pendingQuestion: string | null  // asked, awaiting an answer
  createdAt:       number         // Date.now()
}

QAPair {
  question: string
  answer:   string   // trimmed
}
```

The session is keyed by `sessionId` = `randomUUID()`. `pendingQuestion` is the
single in-flight question; it is set when a question is asked and cleared when
its answer is committed to `history`.

### Report (from `generateReport` / mock)

```
Report {
  overallScore:     number                 // 0–100
  summary:          string
  strengths:        string[]
  improvements:     string[]
  competencyScores: CompetencyScore[]
  perQuestion:      PerQuestionScore[]
}

CompetencyScore   { name: string, score: number /*0–100*/, note: string }
PerQuestionScore  { question: string, score: number /*0–100*/, feedback: string }
```

`ReportStep` defensively defaults every field (`overallScore = 0`, arrays to
`[]`) so a partial or malformed report still renders.

## API / interface contracts

All endpoints are JSON except uploads (multipart) and TTS (audio bytes). Errors
follow `{ error: string, detail?: string }` with an appropriate HTTP status.

### `GET /api/health`
Capability probe.
```
200 → {
  ok: true,
  integrations: { llm: boolean, tts: boolean, stt: boolean },
  roles: [{ id, label, competencies }],
  maxQuestions: number
}
```

### `POST /api/resume` (multipart)
Field `resume` = file. Parses an uploaded PDF/DOCX/TXT.
```
200 → { resume: Resume }
400 → no file       500 → parse failure
```

### `POST /api/resume/text`
```
body: { text: string }
200 → { resume: Resume }
400 → missing text
```

### `POST /api/interview/start`
```
body: { resume: Resume, roleId: string }
200 → { sessionId: string, question: string, questionNumber: 1, maxQuestions: number }
400 → invalid/missing roleId, or missing resume
```
Creates a session, generates the first question, stores it as `pendingQuestion`.

### `POST /api/interview/answer`
```
body: { sessionId: string, answer: string }
200 (more) → { done: false, question: string, questionNumber: number, maxQuestions: number }
200 (end)  → { done: true, questionNumber: number, maxQuestions: number }
404 → unknown/expired session
400 → no pending question
```
Commits the answer to `history`, then either returns an adaptive follow-up or
signals completion when `history.length >= MAX_QUESTIONS`.

### `POST /api/interview/report`
```
body: { sessionId: string }
200 → { report: Report, role: string /*label*/, history: QAPair[] }
404 → unknown/expired session
400 → no answers recorded yet
```

### `POST /api/tts`
```
body: { text: string }
200 → audio/mpeg bytes (MP3)
400 → missing text
501 → TTS not configured   (client falls back to browser speech)
```

### `POST /api/stt` (multipart)
```
field audio = file
200 → { text: string }
400 → no audio
501 → STT not configured    (client falls back to browser recognition)
```

### Client contract nuances
- `serverTTS` returns a Blob URL on success, `null` on `501` or any non-2xx.
- `serverSTT` returns the transcript string, `null` on `501` or any non-2xx.
- These `null` returns are the explicit signal for the client to use the browser
  fallback path, so a missing/failed integration is never surfaced as a hard
  error to the user.

## Interview state machine and adaptive loop

### Frontend phase machine (`App.jsx`)
```
resume ──(resume parsed & role picked, Start)──▶ interview ──(done)──▶ report
   ▲                                                                    │
   └────────────────────── restart ────────────────────────────────────┘
```
`report` can also be reached early via "Finish early & get report", which calls
the same completion path (`handleDone` → `getReport`).

### Per-question loop (`InterviewStep.jsx`)
For each question:
```
1. speak(question)          // server TTS if integrations.tts, else browser
2. startRecording()         // MediaRecorder (server STT path) OR
                            //   BrowserSpeechRecognizer (no server STT)
3. stopRecording()          // → transcript (server Whisper or browser final text)
4. submit()                 // POST /api/interview/answer
5. if res.done → onDone()   // → report phase
   else        → onFollowUp(res.question, res.questionNumber)  // loop
```
The user may also type/edit the answer in the textarea, and may replay the
spoken question. If transcription fails, the user is prompted to type instead.

### Server adaptive loop (`index.js` + `llm.js`)
The server drives adaptation:
```
start:  Q1 = generateFirstQuestion(resume, role)          → pendingQuestion = Q1
answer: history.push({ pendingQuestion, answer })          // commit
        pendingQuestion = null
        if history.length >= MAX_QUESTIONS → { done: true }
        else Qn = generateFollowUp(resume, role, history)  → pendingQuestion = Qn
report: generateReport(resume, role, history)
```
`generateFollowUp` receives the **full transcript** (`history` rendered as
`Q1/A1 … Qn/An`), so each follow-up reacts to prior answers — this is the
adaptive feedback of transcribed answers back into the LLM. `MAX_QUESTIONS = 6`
caps the loop for a bounded demo.

## External integration abstraction with fallbacks

Each integration is isolated in its own module and exposes a boolean `*Configured`
flag derived from environment variables. `index.js` and the client branch on
these flags rather than on try/catch of the integration itself.

### LLM (`llm.js`)
- Configured when `OPENAI_API_KEY` is set (`OPENAI_BASE_URL`, `OPENAI_MODEL`
  override the OpenAI-compatible endpoint/model).
- `chat(messages, { json, temperature })` is the single low-level call; report
  generation requests a JSON object response.
- **Fallback:** when `!llmConfigured`, deterministic mock functions run:
  - `mockFirstQuestion` — greets by name and asks about the top skill/project.
  - `mockFollowUp` — cycles role-specific templates keyed by `role.id`.
  - `mockReport` — heuristic `scoreAnswer` (length + presence of numbers +
    specificity keywords), aggregated into an overall score, competency spread,
    and strengths/improvements.
- **Extra resilience:** even when configured, if the model returns malformed JSON
  for the report, `generateReport` falls back to `mockReport`.

### TTS (`tts.js` + client)
- Configured when `ELEVENLABS_API_KEY` is set (`ELEVENLABS_VOICE_ID`,
  `ELEVENLABS_MODEL` optional). `synthesize` returns an MP3 buffer.
- `/api/tts` returns `501` when not configured.
- **Fallback:** the client only calls `serverTTS` if `integrations.tts`; if that
  returns `null` (or the flag is false), it uses `speakBrowser` (Web Speech
  SpeechSynthesis).

### STT (`stt.js` + client)
- Configured when `OPENAI_API_KEY` is set (reuses the OpenAI key;
  `OPENAI_STT_MODEL` defaults to `whisper-1`). `transcribe` posts audio to the
  Whisper endpoint.
- `/api/stt` returns `501` when not configured.
- **Fallback:** when `!integrations.stt` and the browser supports it, the client
  uses `BrowserSpeechRecognizer` (live Web Speech recognition). When server STT
  is expected but returns `null`, the user is asked to type the answer.

This gives a uniform pattern: **detect capability → prefer server integration →
fall back to browser/mock → allow manual text as the ultimate fallback.**

## Error handling

- **Backend routes** wrap handlers in try/catch, log to `console.error`, and
  return `{ error, detail? }` with status codes: `400` (bad input), `404`
  (unknown session), `500` (integration/parse failure), `501` (integration not
  configured, for TTS/STT).
- **Session lookup** returns `404` for unknown/expired sessions; `answer` returns
  `400` if there is no `pendingQuestion`; `report` returns `400` if `history` is
  empty.
- **Malformed LLM report JSON** degrades to the mock report rather than failing.
- **Frontend `api.js`** throws `Error(data.error || "Request failed (status)")`
  on non-2xx JSON calls; `App`/`InterviewStep`/`ResumeStep` surface the message
  via the `error` banner.
- **Voice failures are non-fatal.** TTS/STT helpers swallow errors and return
  `null`; the interview continues via browser fallback or typed input.
  Microphone permission failure shows a hint to type the answer instead.
- **Health probe failure** shows "Could not reach the backend…" and blocks the
  interview UI (badges/roles are gated on `health`).
- **Upload limits** are enforced by `multer` (10 MB) and `express.json` (2 MB);
  oversized requests are rejected before handler logic.

Known limitations (by design for a demo): sessions are lost on restart; no auth;
no rate limiting; no persistence of reports.

## Testing strategy

The current implementation ships without an automated test suite. The strategy
below targets the seams the code already exposes (pure functions, capability
flags, and the fallback branches) so tests can be added without refactoring.

### Unit tests (backend)
- **`resumeParser.structureResume`** — section splitting, skill dictionary
  matching (word-boundary behavior, `c++`/`c#` escaping), name/summary guessing,
  entry grouping and caps. Feed representative raw text and assert the `Resume`
  shape.
- **`llm` mock functions** — with `OPENAI_API_KEY` unset: `mockFirstQuestion`
  personalization, `mockFollowUp` template cycling per `role.id`, and
  `mockReport` scoring (verify `scoreAnswer` thresholds for length, numbers,
  specifics; overall aggregation; competency spread).
- **`generateReport` JSON-failure path** — stub `chat` to return non-JSON and
  assert it falls back to `mockReport`.
- **`roles`** — `getRole` unknown id → `null`; `listRoles` omits `focus`.

### Integration tests (backend, HTTP)
Exercise the route contracts with a running app (e.g. `supertest`), keys unset so
mocks/`501` paths are used deterministically:
- `GET /api/health` shape and `maxQuestions`.
- `POST /api/resume/text` happy path + `400` on empty.
- Full lifecycle: `start → answer × N → report`, asserting `questionNumber`
  progression, `done:true` at `MAX_QUESTIONS`, and the `Report` shape.
- Error paths: `answer`/`report` with unknown `sessionId` (`404`), `answer` with
  no pending question (`400`), `report` with empty history (`400`).
- `POST /api/tts` and `/api/stt` return `501` when unconfigured.

### Frontend tests
- **`api.js`** — `serverTTS`/`serverSTT` return `null` on `501` and non-2xx;
  `json()` throws with the server `error` message.
- **`App` phase machine** — transitions resume → role → interview → report and
  `restart` resets state (React Testing Library with mocked `api`).
- **`InterviewStep` fallback branching** — with `integrations.stt=false` and
  browser STT available, uses `BrowserSpeechRecognizer`; otherwise records and
  calls `serverSTT`; typed answers submit correctly. Mock `voice.js` and `api`.

### Manual / demo verification
- Zero-key run: mock LLM, browser TTS/STT, full interview to report.
- Keyed run: LLM + ElevenLabs + Whisper produce real questions/audio/transcripts.
- Cross-browser check for Web Speech availability (fallback to typed input where
  `SpeechRecognition` is unsupported).

### Suggested tooling
Node's built-in `node:test` (or Vitest) for backend units; `supertest` for HTTP;
Vitest + React Testing Library for the frontend. No test runner is configured
today, so adding one is the first step before writing the suite.
